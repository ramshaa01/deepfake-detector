## Category 1: Project Walkthrough

**Q: Walk me through this project.**
I built a full-stack binary classifier that detects whether a face image is a real photograph or entirely AI-generated by a GAN. The pipeline covers everything: data curation and face extraction from FFHQ and StyleGAN2 datasets, training and rigorous evaluation of EfficientNet-B0 with transfer learning, Grad-CAM interpretability, an FFT fusion experiment that I ultimately rejected based on evidence, and a live deployment with a FastAPI backend on Render and a React frontend on Vercel. Every metric reported is from a held-out test set; no number is cherry-picked.

**Q: What does it actually do?**
A user uploads a face image to the frontend. The backend runs an OpenCV Haar Cascade to detect and crop the face, feeds the crop through EfficientNet-B0, produces a real/fake label with confidence, and returns a Grad-CAM heatmap showing what the model was looking at. The full API response takes ~446ms server-side, ~2.4s end-to-end from the frontend. The model achieves 84.33% ± 0.34% accuracy on the controlled test set (78.00% in production due to the Haar Cascade replacement).

**Q: What was your role? Who did you work with?**
Solo project, 40 days of daily structured work. I owned every component: dataset selection and curation, training scripts, evaluation methodology, debugging, interpretability, deployment infrastructure, and documentation. I held myself accountable to the same standards I'd use on a team — fixed test splits, no tuning on the test set, documented every methodology change.

## Category 2: ML Fundamentals via This Project

**Q: Why EfficientNet-B0? Why use a pre-trained model at all?**
Training a CNN from scratch on 2,000 images would massively overfit — the model would memorize the training set with no generalization. EfficientNet-B0 pre-trained on ImageNet gives a feature extractor that already knows edges, textures, and shapes from 1.2M images. I only need to teach it what GAN-specific artifacts look like on top of that foundation. I chose B0 specifically over larger EfficientNet variants because I wanted a model that could run on Render's 512MB free tier without quantization — 4.0M parameters is small enough.

**Q: What changed between head-only training and full fine-tuning?**
In head-only training (Days 6-8), the backbone is frozen: only the classifier head (Linear 1280→1) updates its weights. This reached 75.67% accuracy. In full fine-tuning (Days 9-10 and the converged Day 32 run), all layers are unfrozen with differential learning rates — lower learning rates for earlier backbone layers (they contain more general features) and higher rates for the classifier head. Full fine-tuning to 30 epochs with early stopping reached 84.33%. The accuracy gain confirms the backbone needed to specialize to GAN texture artifacts beyond what ImageNet training extracted.

**Q: How did you monitor for overfitting?**
Training and validation loss/accuracy were logged every epoch. I used early stopping with patience=4 on validation accuracy — if val accuracy didn't improve for 4 consecutive epochs, training stopped and the best checkpoint was restored. The Day 32 run stopped at epoch 30 naturally with training and val accuracy tracking closely. I also evaluated on a completely held-out test set (never seen during training or early-stopping decisions) as the final report.

**Q: ROC-AUC vs accuracy vs F1 — what does each actually tell you here?**
Accuracy is the simplest number but is threshold-sensitive: it measures correct predictions at a fixed 0.5 cutoff. F1 combines precision and recall but is also threshold-sensitive and can be distorted by class imbalance. ROC-AUC is threshold-independent — it measures how well the model *ranks* real vs fake across every possible threshold. I relied on ROC-AUC as the primary model comparison metric because it reveals whether one model genuinely discriminates better, without letting a lucky threshold choice manufacture a fake win. This distinction mattered directly: the fusion model appeared to beat CNN-only on accuracy (82% vs 84%), but CNN-only won on ROC-AUC (0.9372 vs 0.9328), exposing the accuracy difference as a threshold artifact.

**Q: What does Grad-CAM do mechanically?**
It computes the gradient of the model's output with respect to the activations of a target convolutional layer (I used `conv_head`, the final conv block). The gradient tells you which activation channels were most influential for that prediction. We pool those gradients spatially, weight the feature maps by those pooled values, and take a ReLU to keep only positive contributions. The result is a heatmap showing which spatial regions of the input most pushed the prediction toward "fake." I implemented it via hooks rather than using an external library, so it works with any backbone architecture.

**Q: What was the FFT radial feature, and why didn't it help?**
StyleGAN2's upsampling via transposed convolutions introduces periodic artifacts in the frequency domain — you can see peaks in the radial spectral profile around 0.3–0.5 normalized frequency that don't appear in real photographs. I extracted a 16-bin radial average of the magnitude spectrum as an auxiliary feature and built a CNN+FFT fusion head. It gave 79.33% accuracy vs the CNN-only baseline of 75.67% at the time. But once the CNN backbone was fully fine-tuned to convergence (Day 32), the CNN alone learned to detect those spectral cues from raw pixels. The fusion model lost on ROC-AUC and was 17% slower — adding the explicit frequency feature was redundant post-convergence.

## Category 4: Architecture and Design Decisions

**Q: Why EfficientNet-B0 specifically over VGG, ResNet, etc.?**
EfficientNet-B0 has a favorable accuracy-per-parameter tradeoff due to compound scaling — it scales depth, width, and resolution together rather than independently. VGG and early ResNets are far larger for comparable accuracy. XceptionNet is the field-standard baseline for GAN face detection; I explicitly trained and evaluated it on Day 35 and confirmed EfficientNet-B0 outperforms it: 84.33% vs 81.60% accuracy, 0.9321 vs 0.9120 AUC, with 5× fewer parameters (4.0M vs 20.8M).

**Q: Why was fusion tried, then rejected?**
At Day 16, the CNN backbone was not fully trained (the run was interrupted at epoch 7). The FFT fusion gave a visible accuracy lift over that weak backbone. It was a reasonable hypothesis worth testing. On Day 32, with a properly converged backbone, I retested using a matched-operating-point analysis — the same methodology I'd developed in Day 16-17 — and found CNN-only wins on ROC-AUC at every operating point, and is 17% faster. I rejected fusion because the evidence was unambiguous, not because I had a prior preference for simpler models.

**Q: Why Haar Cascade in production vs MTCNN in training?**
MTCNN requires TensorFlow as a dependency — that adds ~400MB of RAM. Render's free tier allows 512MB total, which leaves less than 100MB for the PyTorch model, inference overhead, and the container OS. MTCNN would crash the service on the first request. Haar Cascade is ~100KB with zero deep-learning dependencies. The cost is fully measured: −6.00pp accuracy (78% vs 84%), −0.0985 AUC (0.8387 vs 0.9372), 14/300 detection failures (4.7%). I documented this gap explicitly rather than quoting the MTCNN number in production.

**Q: Why FastAPI / Render / Vercel?**
FastAPI because it gives automatic request validation, OpenAPI/Swagger docs from type hints, and async support with minimal boilerplate — it's the production standard for Python inference APIs. Render because it offers a free tier with Docker support and persistent containers (unlike Lambda), which matters for loading a 4M-parameter model on startup without a cold-start penalty every request. Vercel because it's the zero-ops standard for React/Vite frontends with global CDN — the frontend is a static build, so it's free and near-instant to deploy. The two services are independently deployed, which means frontend changes don't require redeploying the model.

## Category 5: Metrics and Statistics Questions

**Q: Is 84% good?**
It's meaningfully above random (50%), and it outperforms the field-standard XceptionNet baseline on the same test set (81.6%). The dataset is balanced so there's no accuracy inflation from class skew. It's not a state-of-the-art result on a benchmark leaderboard — the training data is only 2,000 images from a single generator, which limits both the ceiling and the generalizability. For a single-generator detector built to prove out the full pipeline end-to-end, 84.33% ± 0.34% with a 0.9321 AUC is a solid, honestly-reported result.

**Q: How do you know this isn't overfitting?**
Three lines of evidence. First, training and validation curves tracked closely throughout the Day 32 run — no divergence between them. Second, the final metrics are reported on a held-out test set (300 images) that was never used during training or hyperparameter selection. Third, I ran the same architecture with three different random seeds: 84.00%, 84.33%, 84.67% — the spread is ±0.34%, which is extremely low variance and confirms the result is stable and not a lucky initialization.

**Q: Why report mean ± std instead of a single number?**
A single training run can be a lucky or unlucky initialization. Two runs that give 84% and 85% look identical in headlines but might reflect very different stability. Reporting mean ± std across 3 seeds explicitly quantifies how sensitive the result is to initialization. It also makes the headline defensible: if someone says "maybe you got lucky," the answer is "the variance is 0.34%, which means any run from this methodology gives a result between 84.0% and 84.7%."

**Q: What's calibration and why does ECE matter?**
Calibration measures whether a model's confidence scores reflect actual probabilities. A model with ECE=0 is perfectly calibrated: when it says 80% confidence, it's right 80% of the time. ECE (Expected Calibration Error) quantifies the average gap between predicted confidence and true accuracy across probability bins. This model's ECE is 0.0687 — reasonable, below 0.10. It matters because the `/predict` endpoint returns a `confidence` field, and if the model were overconfident (ECE=0.30+), that confidence score would mislead downstream decision-making. At ECE=0.0687, the confidence values are usable as-is.

**Q: What would you do with more data or compute?**
With more data: multi-generator training (StyleGAN2 + StyleGAN3 + Stable Diffusion + Midjourney) to break the current OOD collapse. With more compute: MTCNN in production (eliminating the 6pp delta), and proper hyperparameter search with a tool like Optuna. With more time: a fairness audit across demographic groups (skin tone, age, gender), and adversarial robustness testing — can a generator be fine-tuned to specifically evade this detector?

## Category 6: Failure Modes and Limitations

**Q: Tell me about the eyeglasses false-positive bias.**
Grad-CAM analysis (Day 13) showed the model firing strongly on nose bridges and eyeglass frames when predicting "fake" on real photos of glasses-wearers. The root cause is a training data distributional mismatch: StyleGAN2 struggles to render symmetric eyeglass frames, so the FFHQ real-photo class contains far more glasses than the StyleGAN2 fake class. The model learned glasses as a spurious proxy for "real human," and fires on their absence. Real people wearing glasses will see elevated false-positive (predicted fake) rates. The fix is more diverse fake data with glasses, or data augmentation that forces the model off this shortcut.

**Q: What causes the collapse under blur or downscaling?**
Under heavy Gaussian blur (σ≥2) or extreme downscaling (0.25×), the real image accuracy falls to 10–23% while fake accuracy stays high (82–98%). The model becomes an indiscriminate fake-predictor. The most likely cause is the same as the GAN-artifact story told in reverse: the CNN learned to detect high-frequency textural details that distinguish real photos from GAN fakes. Blur and downscaling destroy those high-frequency signals. With them gone, the model defaults to predicting fake because that's the safer low-frequency guess. This is not recoverable by threshold tuning — the information is gone.

**Q: Why does it fail so completely on StyleGAN3?**
Overall accuracy falls from 78% to 46.67% (below random), and fake-detection accuracy drops to 4.00% — it correctly identifies only 3 out of 75 StyleGAN3 fakes. The model learned to detect transposed-convolution grid artifacts, which appear as regular patterns in the frequency domain at ~0.3–0.5 normalized frequency. StyleGAN3 specifically redesigned its synthesis process to be alias-free using continuous coordinate representations and ideal low-pass filters. Those grid artifacts are entirely suppressed. Without the learned signal present, the model has no basis for a fake prediction and classifies everything as real.

## Category 7: System Design and Deployment Questions

**Q: How do the two services (Vercel + Render) communicate?**
The Vercel frontend is a static React/Vite build served from Vercel's CDN — it contains no backend logic. When a user uploads an image, the frontend JavaScript makes a POST request to the Render backend URL (`https://deepfake-detector-k62g.onrender.com/predict`). The backend processes the image and returns JSON containing the label, confidence, and a base64-encoded Grad-CAM heatmap JPEG. The frontend decodes the base64 and renders the heatmap inline. CORS is configured on the FastAPI backend to allow requests from the Vercel domain.

**Q: What happens on a cold start?**
Render's free tier spins down containers after 15 minutes of inactivity. On the first request after idle, the container must restart (~5–15s), import PyTorch and timm (~10–20s), and load the 4.0M parameter checkpoint from disk into CPU memory (~5s). Total cold-start time: 30–90 seconds. Subsequent requests within the same session are fast (~446ms Full API response). The frontend handles this gracefully — after 5 seconds of no response, it shows a "waking up the server, please wait" message.

**Q: How does rate limiting work?**
The FastAPI backend uses `slowapi` (a Starlette-compatible wrapper around `limits`) to enforce 10 requests per minute per IP address. The IP is extracted from `X-Forwarded-For` headers (set by Render's proxy) via `get_remote_address`. Requests exceeding the limit receive a 429 response with a descriptive error message. This prevents a single client from monopolizing the free-tier backend or running the model for brute-force purposes.

**Q: What would you add for real production use?**
At minimum: authentication on the `/predict` endpoint (currently open — any request goes through), structured logging and monitoring (Datadog or similar — currently only `print` statements), and a paid deployment tier to get MTCNN back and eliminate the 6pp production gap. For a trust & safety application: a confidence threshold higher than 0.5 (to reduce false positives, accepting some false negatives), a human-in-the-loop review queue for borderline scores (0.4–0.6), and a scheduled retraining pipeline with new generator data as adversarial GANs evolve.

## Category 8: "Gotcha" Questions

**Q: Your test set is only 300 images — how much do you trust these numbers?**
The 300-image test set is small enough that any single run has meaningful uncertainty. That's exactly why I ran three seeds: the spread is 84.00%–84.67% (±0.34%), which demonstrates that the result is not noise-dominated. The ROC-AUC spread is 0.9267–0.9372 (±0.0053), also very tight. I'd acknowledge the dataset size as a real limitation — a 3,000-image test set would give narrower confidence intervals — but the multi-seed variance gives me confidence that the 84.33% headline is representative of this methodology, not a single lucky initialization.

**Q: Why didn't you use a bigger or more diverse dataset?**
The explicit choice was to build the full pipeline end-to-end with a manageable, well-understood dataset first. FFHQ and StyleGAN2 are the canonical pair for this task in the academic literature, which also makes the result comparable to existing work. Scaling to 50,000 images with multiple generators is the right next step, but building the evaluation methodology and deployment infrastructure with 2,000 images first meant I could validate every component carefully without waiting on a multi-day training run.

**Q: This doesn't generalize to StyleGAN3, so what's it actually useful for?**
It's useful as a StyleGAN2-artifact detector, not as a general synthetic-face detector. In practice, many synthetic profile generation services still use StyleGAN2 or architecturally similar models because StyleGAN2 checkpoints are widely distributed and well-documented. More importantly, the project demonstrates the *methodology* — the training pipeline, the evaluation rigor, the deployment architecture, and the failure-mode documentation — all of which transfer directly to a multi-generator version. A production-grade detector would train on StyleGAN2 + StyleGAN3 + diffusion-based faces; this establishes the infrastructure to do that.

**Q: Why is your production accuracy lower than your reported accuracy?**
This is a documented and fully measured constraint, not a methodology error. The controlled evaluation uses MTCNN for face extraction (same detector used during training) — that's 84.33%. The production deployment on Render's 512MB free tier cannot fit MTCNN/TensorFlow (~400MB dependency), so I switched to OpenCV Haar Cascades. Haar Cascade fails to detect a face entirely in 14/300 test images (4.7%), and produces different-quality crops on the rest. The production system accuracy — measured by running the exact production pipeline, including penalising detection failures — is 78.00%. The 6pp gap is a resource constraint, fully disclosed, with a known fix (larger deployment tier or MTCNN distillation).

## Category 9: What Would You Do Differently / What's Next

**Adversarial robustness testing.** Can a generator be specifically fine-tuned to evade this detector? This is the attack vector that would matter in a real trust & safety context. The current model has never been tested against adversarially crafted inputs. An adversarial evaluation would reveal exactly what signal the model relies on and whether it can be suppressed cheaply.

**Fairness audit across demographic groups.** No analysis has been run on whether the model's false-positive rate varies by skin tone, age, or gender. FFHQ has documented demographic biases toward lighter skin tones and certain age ranges; it's plausible the model has learned spurious correlations from those. A properly scoped deployment would require a demographic parity analysis before use in any moderation context.

**Experiment tracking tooling.** All training runs were tracked manually — CSVs, Markdown reports, per-run files. With more than 3 seeds this would break down. A tool like MLflow or W&B would have made variance analysis automatic and made it easy to reproduce any specific run. Adding this early would have saved the manual bookkeeping across Days 37–39.

**Authentication and monitoring on the API.** The current `/predict` endpoint is fully open. In production, this needs at minimum an API key or OAuth token to prevent abuse, and structured observability (request counts, latency percentiles, error rates) so degradation is detectable before users notice.

**Multi-generator training.** The Day 36 OOD evaluation proved the model is useless against StyleGAN3. Training on a multi-generator dataset (StyleGAN2 + StyleGAN3 + Stable Diffusion faces + Midjourney) with appropriate data augmentation is the single highest-leverage improvement — it would convert this from a StyleGAN2-artifact detector into something genuinely useful for real-world content moderation.
